# Промты для Codex (GPT-6.1 Sol)

Памятка для всех, кто пишет задачи для Codex в этом репозитории. Владелец работает с **GPT-6.1 Sol**. В настройках Codex у него стоит «Ультра»: у OpenAI нет такого режима, это либо Ultrafast (быстрая генерация токенов, на качество не влияет), либо максимальный уровень рассуждений. Перед тем как подгонять промт, проверьте, что выбрано.

Источник: руководство OpenAI по семейству GPT-6 («A model guide for the GPT-6 family», «Rethinking skills and prompts for GPT-6 Astra», «Using GPT-6»). Страница руководства не открывается напрямую (403), поэтому цитаты взяты из конспекта, который собран по её копиям. Цены и результаты тестов сюда не вошли: они не нужны для составления промтов.

## Главные правила

1. **Результат, а не рецепт.** Опишите, что должно получиться, для кого, какой контекст и что считается готовым. Длинные пошаговые инструкции теперь вредят: «overly specific guidance can now hinder results where it previously helped».
2. **«Готово значит…».** Перечислите проверяемые условия: изменение сделано, запущено, результат проверен, сбои исправлены. Без этого модель может остановиться на первой реализации.
3. **Минимальная правка.** Модели склонны превращать точечные правки в рефакторинг. Всегда пишите: минимально необходимый набор изменений, архитектуру и несвязанные файлы не трогать.
4. **Границы решений вместо «всегда спрашивай».** Скажите, что можно решать самой (раскладка, названия, мелкие размеры) и когда спрашивать (смена объёма задачи, версия, данные пользователей).
5. **Не заставлять читать всё подряд.** «Прочитай всё перед каждой правкой» жжёт контекст. Указывайте документы по ситуации: схема базы для изменения схемы, раздел AGENTS.md для нужной области.
6. **Проверки модель запускает сама.** Не напоминайте «запусти тесты». Пишите, что проверить и чего не запускать (для правки вёрстки полный набор тестов не нужен). Перезапускать только при новой ошибке.
7. **Без капса и тотальных запретов.** Оставляйте только настоящие запреты: версия в `pubspec.yaml`, нативные снимки и перезагрузка WebView, ключи и секреты.
8. **Без непрошеных предупреждений.** Модель не должна добавлять дисклеймеры и чек-листы безопасности из-за гипотетических рисков.
9. **Субагенты — по явной просьбе.** По умолчанию модель почти не делит работу. Для крупных задач просите проверить независимые части параллельно.
10. **Постоянное в начале, меняющееся в конце** (кэш запроса). Вступление про `git`, `setup` и AGENTS.md одинаково во всех промтах, скриншоты и логи ближе к концу.
11. **Короткий итог в конце:** что изменилось, что проверено, что осталось, простым языком.
12. **Стиль текста** (для docs/releases и отчётов): простые глаголы, абзацы с одной мыслью, без «стоит отметить», «важно», «в общем», выдуманных составных ярлыков и размытых уточнений; пробелы между словами и числами.

## Шаблон

```
cd /workspace/Moru
git fetch origin claude/moru-v0-1-16-audit-s69yji
git checkout -B claude/moru-v0-1-16-audit-s69yji FETCH_HEAD
bash tool/codex_cloud_setup.sh
source "$HOME/.moru-toolchains/activate.sh"
Дальше следуй AGENTS.md. PR — с базой claude/moru-v0-1-16-audit-s69yji.

Задача: <результат, который нужен пользователю, и для кого>.
Контекст: <что уже есть, нужные файлы>.
Границы: минимально необходимый набор изменений, архитектуру и несвязанные файлы не трогай. Версия остаётся 0.1.47+48.
Решай сама: <мелочи, которые можно выбрать без вопросов>. Спроси, если нужно изменить объём задачи или трогать данные пользователей.
Готово значит: <проверяемые условия>. Исправь и то, что сломалось из-за твоей правки.
Проверка: <что запустить и что не запускать>.
В конце: короткое резюме простым языком (что изменилось, что проверено, что осталось).
```

Если владелец просит не гонять тесты локально, оставьте только `dart format` по изменённым файлам и `dart analyze --fatal-infos lib test integration_test`: остальное прогонит CI.

## Примеры из руководства

Описание навыка (skill):
- плохо: «Use when working with databases, queries, models, or persistence» (срабатывает на любое упоминание базы);
- хорошо: «Use when adding or changing a migration, or reviewing its rollout».

Чтение документации в AGENTS.md:
- плохо: «Before every edit, read architecture.md, database.md, and deployment.md»;
- хорошо: «Use architecture.md for service boundaries, database.md for schema changes, and deployment.md when preparing a deployment».

Разрешение на проверки:
> The local tests use disposable fixtures and have no production access. Run them, fix failures caused by the requested change, and rerun affected tests without asking for approval at each step.

## Длинные задачи

- **Mid-turn steering:** поправку можно отправить, пока модель работает. Она встаёт в очередь и не отменяет запущенные инструменты. В поправке укажите, что изменить и что оставить.
- **Асинхронные инструменты:** модель продолжает независимую работу, пока идёт медленная задача (например, тесты), и ждёт результат перед зависимой работой.
- **Compaction:** при длинных диалогах контекст сжимается с сохранением состояния.
- **Skills:** короткие описания с точным условием срабатывания, корневой документ как «маршрутизатор» на вспомогательные файлы, явный приоритет инструкций пользователя над навыком.

## Для вызовов через API (не для Codex)

- GPT-6 Astra и GPT-6.1 Sol не принимают `reasoning.effort = none`, используйте `low`.
- При включённых рассуждениях уберите `temperature`, `top_p`, `logprobs`, `top_logprobs`.
- Менять уровень рассуждений лучше, не меняя начало запроса, чтобы не потерять кэш.
