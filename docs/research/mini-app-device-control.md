# Мини-приложения Moru для управления телефоном

Исследование от 5 октября 2026 года. Проверен код базовой ветки `claude/moru-v0-1-16-audit-s69yji`, коммит [`544bf75b`](https://github.com/mishaqp/Moru/commit/544bf75b6e8c0748cab2c06baae6d2b5ee5a5718), версия **0.1.47+48**. В базе уже объединён [PR #106](https://github.com/mishaqp/Moru/pull/106) с общим контрактом схем инструментов.

Это предложение для будущих изменений. Код приложения, тесты, CI и версия в рамках исследования не меняются. Команды на телефоне не выполнялись. Факты о Moru получены чтением исходников; возможности Android и Termux сверены с первичными источниками в конце документа. Сравнение скорости и расхода ресурсов качественное: замеров на устройстве нет.

## 1. Короткий ответ

**Идея реальна, если делать мини-приложение экраном над проверенными возможностями Moru.** ИИ и кнопки должны вызывать один и тот же обработчик действия. Для панели батареи браузер и отдельный Linux-сервер не нужны.

| Часть идеи | Вывод | Что это означает для пользователя |
| --- | --- | --- |
| ИИ создаёт небольшую программу с кнопками | **Реально.** HTML-приложения уже есть; экран из готовых Flutter-компонентов нужно добавить. | ИИ сможет собрать панель из карточек, кнопок, переключателей и ползунков. |
| Заряд, зарядка, температура батареи | **Реально без root.** Нужен новый нативный API. | Панель получает сведения непосредственно от Android. Температура батареи — не температура процессора. |
| Текущий расход, остаток времени и износ | **Частично.** Доступность и качество датчиков различаются. | Ток и расчёт времени можно показывать с оговоркой; точный износ и гарантированное время работы обещать нельзя. |
| Какие приложения расходуют заряд | **Частично.** Время использования доступно с разрешением; расход энергии — другая информация. | Без повышенных прав надёжнее открыть системный экран батареи. Через root/ADB можно разбирать системную статистику, но это оценки. |
| Включить системное энергосбережение | **Частично.** Читать состояние и открыть настройки можно без root; напрямую менять — с повышенными правами. | Без root кнопка ведёт в настройки. С root переключение выполняет Moru. Shizuku может стать отдельным вариантом без root. |
| Менять яркость | **Реально.** Для общей яркости нужно разрешение Android. | Только яркость окна Moru меняется без него; это отдельный режим. |
| Ограничивать чужие фоновые приложения, менять общую частоту экрана | **Частично.** Нужны настройки пользователя либо root/ADB; многое зависит от прошивки. | Универсальной кнопки для любого телефона не будет. Некоторые ограничения ломают уведомления. |
| ИИ в чате вызывает действие приложения | **Реально, но пока отсутствует.** Сейчас чат меняет данные и запускает задания. | Нужно добавить объявления действий, их инструменты ИИ и общий исполнитель. |
| Работать с установленным Termux | **Реально, но интеграции сейчас нет.** | Потребуются разрешение и настройка Termux. Для батарейной панели Termux не нужен. |
| Использовать встроенный Linux Moru | **Реально, частично уже есть.** | Подходит для Python/Node и обработки данных, но сам по себе не даёт прав управления Android. |
| Быстро отвечать и почти ничего не расходовать в покое | **Реально как цель, требует измерений.** | Нативная панель без постоянно работающих процессов — наиболее подходящий путь. Абсолютный «нулевой расход» обещать нельзя. |
| Управлять всем на любом Android без root и настройки разрешений | **Нет.** | Ни выбор движка, ни ИИ, ни Termux не отменяют ограничения Android. |

Рекомендация: **гибрид с единым API действий**. Панели управления — декларативный экран Flutter и нативные обработчики. Игры и богатые веб-приложения — существующий WebView. Linux и Termux — дополнительные исполнители для задач, которым действительно нужны их программы. Лёгкий JS-движок добавить позже, если готовых действий и простых правил станет мало.

### Существенные особенности безопасности текущего кода

1. В `LocalToolNames.requiresApprovalFor` **`phone_control` не требует отдельной карточки подтверждения**. Требование согласия перед покупкой/отправкой/удалением написано в описании инструмента для модели; нативный сервис такие последствия не классифицирует. Поэтому нельзя считать этот путь готовой системой подтверждений device API.
2. При `SERVICE_UNAVAILABLE` `ToolHandlerService` может перейти на `RootPhoneControl`, если у текущего ассистента включён `root_shell`. Fallback вызывает `RootShellTool.run` напрямую. Отдельного root-подтверждения в этой ветке нет, а проверки свежести снимка и блокировки не совпадают с Accessibility. Это установленное чтением кода расхождение, а не проверенная атака на телефоне.
3. `root_shell` принимает произвольную команду. Его `isReadOnly` решает, спрашивать ли подтверждение; это **не белый список разрешённых команд**. В частности, `dumpsys` может содержать изменяющие подкоманды. Ограничения и отложенная работа уже описаны в [аудите, D3/D4/D8/D9](../audits/model-tools.md).
4. `server.command` исполняется через активный Linux-runtime. При включённом root chroot сервер тоже получает настоящий root; `moru_chroot.c` не сбрасывает UID/capabilities. Обойтись белым списком методов `moru.device` недостаточно, если тому же приложению остаётся доступна произвольная привилегированная программа.
5. PRoot и chroot не отделяют недоверенные приложения как Android-песочницы. [ProotCommand.kt](../../android/app/src/main/kotlin/com/psyche/kelivo/workspace/ProotCommand.kt) прямо предупреждает об отсутствии изоляции произвольных shell-программ и фактической записываемости PRoot read-only binds. Root chroot создаёт mount namespace, но сохраняет root и доступ к host `/proc`, `/dev`, `/sys`.

**Вывод:** существующие функции полезны как строительные блоки. Новому device API нужны собственные проверки прав на всех входах. Ограниченные приложения не должны автоматически наследовать root Linux, произвольный shell, права Termux или доступ из Wi-Fi.

## 3. Какой движок выбрать

Экран и исполнитель действия — разные вещи. Для смены яркости не обязательно запускать код экрана. ИИ может выполнить нативное действие, даже если мини-приложение закрыто.

В таблице сравнивается добавление мини-приложения **к уже работающему Moru**. Холодный запуск самого Moru, Flutter и получение root-разрешения добавят свою задержку при любом варианте. Значений в миллисекундах/мегабайтах нет: их нужно измерять на одинаковом телефоне.

| Вариант | Запуск и плавность | Батарея и память | Размер APK | Как писать ИИ | Безопасность и объём работы |
| --- | --- | --- | --- | --- | --- |
| **А. Текущий WebView, HTML/JS** | Холодный старт создаёт WebView, загружает страницу и JS. Простая страница может быть плавной; тяжёлый DOM, таймеры и мост мешают. Canvas/WebGL подходят для графики. | Обычно больше памяти, чем небольшое дерево уже имеющихся Flutter-виджетов. В покое может быть экономным, если остановлены таймеры/анимации; скрытая страница с циклом продолжает стоить ресурсов. | Системный WebView не надо целиком класть в APK; зависимость уже есть. Большие библиотеки и ассеты увеличивают размер самих приложений. | Знакомые HTML/CSS/JS; много готовых библиотек. | Основная инфраструктура уже есть: доработки относительно небольшие. Нужна проверка происхождения запросов, сети и возможностей моста. Произвольный JS требует ограничений. |
| **Б1. JSON-экран Flutter + готовые нативные действия** | Нет запуска браузера/скрипта. Moru создаёт карточки, кнопки и ползунки в своём стиле. Нативный код тоже может тормозить, если делать тяжёлую работу на UI-потоке. | Flutter уже в APK; добавляются компоненты/обработчики и описание формата, без нового VM. | ИИ заполняет небольшую понятную схему и выбирает известные действия. Lua тоже лёгкий, но требует отдельного языка/SDK. | Большая работа: очередь, async API, лимиты памяти/стека/времени, прерывание, обновления библиотеки. Сам VM не является Android-песочницей. |
| **В. Python/Node в Linux + экран А или Б** | Прогретый сервер может быстро отвечать. Холодный старт включает runtime, процесс, imports и проверку готовности. ### Что в текущем WebView может замедлять работу

По коду подтверждены создание нового `WebViewController` при открытии, загрузка `file://` и передача каждого `moru.*` вызова через JSON → канал → Dart → JavaScript-ответ. Каждый `storage.get` читает и разбирает `data.json`; запись переписывает весь JSON с `flush` и атомарным переименованием. Лимит данных — 5 MiB. Если запрашивать много ключей и сохранять показания часто, накладные расходы будут лишними. Это **кандидаты на задержку**, а не доказательство текущих лагов.

У приложения с сервером аренда начинается при открытии. Поэтому небольшая веб-панель может ещё запускать Linux, даже если её экран почти пуст. Сервер имеет таймаут готовности 120 секунд; это верхняя граница ожидания, не измеренная длительность запуска. Фоновое задание загружает тот же HTML, включая не нужный ему UI-код.

У Flutter и WebView разные системы отрисовки. Их совмещение через Platform Views может ухудшать кадры при сложных наложениях и анимациях [E1]. Но у Android 10+ нет основания автоматически приписывать каждому кадру старую двойную GPU-копию Android 9 и ниже. Документация Flutter сейчас описывает более новый SDK, чем установленный в Moru: экспериментальные режимы композиции нельзя объявлять готовой оптимизацией этой ветки.

Разумные улучшения WebView в будущих PR:

- Маленький локальный bundle без обязательных CDN и тяжёлого фреймворка; обновление DOM частями, `requestAnimationFrame` для анимации, остановка скрытой анимации/аудио.
- Один снимок состояния вместо десятков переходов через мост; кэш чтения с корректным сбросом, пакетирование изменений, редкие записи истории на диск.
- Никаких `setInterval` с опросом батареи, `dumpsys` или AI-запросов каждые секунды. События приходят от Android.
- Проверить управление страницей при сворачивании и уничтожении. Сохранять данные отдельно, а не держать WebView постоянно ради следующего быстрого открытия. Если когда-нибудь нужен кэш контроллеров — только ограниченный и измеренный.
- Для нового привилегированного bridge перейти к проверяемому origin и безопасной загрузке локальных ресурсов: Android рекомендует `WebViewAssetLoader`/HTTPS-подобный origin вместо расширения доступа `file://` [E2], [E3]. Ограничение навигации само по себе не ограничивает все iframe/ресурсы/сетевые запросы.
- Действия ИИ выполнять вне страницы. Скрытый WebView оставить для совместимости JS-заданий, которым действительно нужен браузер.

### Рекомендация по движку

**Для панелей:** начать с Б1. ИИ описывает экран JSON: карточка батареи, статус энергосбережения, кнопка настроек, ползунок яркости. Moru рисует их уже имеющимися компонентами, например [SectionCard](../../lib/shared/widgets/section_card.dart) и [ios_settings_rows.dart](../../lib/shared/widgets/ios_settings_rows.dart), с темой и размерами элементов Moru. Формат должен поддерживать только ограниченный набор компонентов, привязки к состоянию и известные действия. Не выполнять строки как Dart/JS и не загружать нативные плагины из приложения.

Первой панели достаточно нативных обработчиков. Это проще, меньше по объёму и не требует выбрать/упаковать VM до получения полезного результата. **QuickJS — предпочтительный следующий кандидат**, если понадобится пользовательская логика: язык JS совпадает с веб-приложениями. Lua имеет смысл при конкретной потребности, а не для добавления второго языка. QuickJS без прямого файлового/сетевого/shell-доступа, с лимитами и прерываниями — лишь часть защиты [E4]; для недоверенных скриптов отдельно оценить Android `isolatedProcess` с доступом только через брокер [E5]. Обычный отдельный процесс с тем же UID такой изоляции не даёт.

**Для игр и богатых приложений:** сохранить А. WebView уже умеет Canvas, WebGL, звук, CSS и браузерные библиотеки; JSON-панель не заменяет их. Простые Flutter-графики можно добавить в формат панели позже. Отдельный игровой движок, например Flame, потребует своего API/формата и не сделает произвольный генерируемый Dart исполнимым без сборки. Для первого этапа это лишняя работа.

**Linux:** выбирать для анализа журналов, обработки файлов, сложных библиотек и сетевых сервисов. Не отправлять в Python запрос «установи яркость», который Android может выполнить напрямую.

## 4. Возможности Android 10–15

Доступ делится на три разных уровня:

- **Обычный APK:** публичные API и разрешения, которые пользователь выдаёт в Android.
- **Повышенный доступ без root:** ADB, Shizuku либо отдельные разрешения, выданные через ADB. Это не стандартное разрешение с кнопкой «Разрешить» и не полный root.
- **Root:** телефон уже имеет root, и root-менеджер разрешил его Moru. Полный доступ внутри Moru этого не создаёт.

В колонке «root» приведены известные семейства команд **для будущего фиксированного обработчика**, а не предложение исполнить их в этой исследовательской задаче. Некоторые команды доступны также shell-UID через ADB/Shizuku; их нельзя честно называть исключительно root-командами.

### Что меняется между Android 10 и 15

- **Android 10:** ограничения запуска экранов из фона, Wi-Fi setters и scoped storage; для современных target SDK также ограничено исполнение из writable app-home. Нельзя без проверки переносить способы запуска Termux в Moru [T6].
- **Android 11:** видимость установленных пакетов ограничена; интеграции Termux нужны точные `<queries>`, а не требование видеть все приложения. Доступ к `Android/data` через общий файловый picker ограничен. UsageStats должен учитывать состояние разблокировки [A4], [A7].
- **Android 12:** фоновые старты foreground service ограничены для соответствующих target SDK; точные будильники имеют отдельный доступ. Высокая частота «будить приложение ради проверки» и ненадёжна, и расходует батарею [A8], [A11].
- **Android 13:** отдельное разрешение уведомлений; sideload-приложения могут потребовать пользовательского снятия Restricted settings для Accessibility/Notification Listener. Это не повод включать такие права автоматически.
- **Android 14–15:** усилены правила foreground service, его типов, PendingIntent и запуска Activity из фона. Не все ограничения одинаковы для разных target SDK. При target 35 разрешение overlay само по себе не гарантирует право начать сервис из фона: для соответствующего исключения нужен видимый overlay [A8]. У `dataSync`/`mediaProcessing` при target 35 есть лимит по шесть часов за 24 часа для каждого типа; нельзя маскировать вечный мониторинг под синхронизацию. Это не утверждение, что данный лимит относится к нынешнему `specialUse` Moru; общий режим фона всё равно не безусловен.

Для всех версий имеют значение прошивка, target SDK Moru/Termux, root-менеджер, рабочий профиль, зарядка и режимы самого производителя. [AndroidManifest.xml Moru](../../android/app/src/main/AndroidManifest.xml) уже объявляет Usage Access, Accessibility-сервис и уведомления, но **не объявляет** `WRITE_SETTINGS`, `WRITE_SECURE_SETTINGS`, `BATTERY_STATS`, `DUMP` или `com.termux.permission.RUN_COMMAND`. Чтение BatteryManager не требует добавлять их. Android-версию и доступные методы нужно проверять при выполнении.

## 5. Termux и встроенный Linux

### Что действительно можно подключить

**RUN_COMMAND — основной путь** [T1], [T2]. Moru отправляет explicit Intent в `com.termux.app.RunCommandService`, с действием `com.termux.RUN_COMMAND`, исполняемым файлом, массивом аргументов, рабочей папкой и режимом выполнения. Для этого Moru должен объявить и получить пользовательское разрешение `com.termux.permission.RUN_COMMAND`; в Termux требуется `allow-external-apps=true` в `~/.termux/termux.properties` и перезагрузка настроек. Одинаковая подпись **Moru и Termux для RUN_COMMAND не нужна**.

Для фонового выполнения можно получить stdout, stderr и exit code через PendingIntent. Для терминальной сессии формат результата отличается: общий transcript. Документированное ограничение stdout+stderr в callback — 100 KB, поэтому большие данные передавать файлом/потоком. Callback нужен с explicit компонентом, уникальной идентичностью вызова и корректным mutable-флагом для добавляемых Termux полей; его нельзя открывать произвольным отправителям или использовать как команду на автоматическое открытие Activity. Отмена/смерть Moru, запуск Termux и потеря результата требуют отдельного lifecycle. RUN_COMMAND не является готовым потоковым STDIO/PTY-протоколом: интерактивный stdin, live output и остановку длительной программы нужно решать отдельно. Launch extras/секреты могут попасть в verbose-журнал Termux; не передавать туда ключи Moru без отдельного защищённого контракта.

**Termux:API** [T3] даёт терминальным командам доступ к Android-функциям: например, `termux-battery-status`, `termux-brightness`, уведомления и некоторые датчики. Нужны совместимые Termux и Termux:API, пакет `termux-api` внутри Termux, разрешения API-приложению. Их подписи/источники установки должны соответствовать требованиям выбранной сборки. Это **не** требование подписывать Moru ключом Termux. Прямой вызов внутреннего receiver Termux:API из Moru не подходит: upstream использует shared UID/signature, receiver не экспортирован. Вызывать API через программу, запущенную **в Termux**.

`termux-brightness` не даёт Moru права менять всю систему без настройки, а `termux-battery-status` не открывает точную энергию всех приложений. Termux:API получает только те права, которые ему разрешил Android. Вывод/набор команд проверить на версии пользователя, в особенности для сборок из разных каналов.

**Файлы** [T4]: Moru не может просто читать приватный `/data/data/com.termux/...`. Можно использовать пользовательский выбор через SAF — системный доступ к выбранным URI, Termux DocumentsProvider; upstream также имеет файловый ContentProvider под RUN_COMMAND и `allow-external-apps`. Это обмен содержимым/дескрипторами, а не общий каталог с полными правами. Общая память требует настройки `termux-setup-storage` и учёта scoped storage; для ключей и рабочих секретов она не подходит.

**Сокеты/localhost:** Termux и Moru могут связываться по TCP на `127.0.0.1` в общей сети Android. Unix-socket в приватном каталоге чужого UID обычно недоступен. Нужны случайный токен, проверка клиента/Origin, лимиты и остановка сервера. «Это localhost» не значит «другие приложения телефона не могут подключиться». Не открывать такой управляющий сервер на `0.0.0.0` без отдельного решения о удалённом доступе.

**Общие пакеты** [T5]: простой общий `node_modules`, Python-prefix или каталог `usr` — ненадёжная идея. Termux использует Android/bionic и свой встроенный путь установки; Linux-rootfs — glibc/musl и другую файловую структуру. Android UID/SELinux не разрешают произвольное чтение private prefix. Исходники и переносимые данные можно обменивать; бинарники, native Python-модули и Node addons лучше устанавливать отдельно в каждом окружении. Наличие в Moru PRoot/PTy-компонентов происхождения Termux **не означает** установленный Termux или готовую интеграцию с ним.

### Что придётся настроить пользователю

1. Установить подходящую сборку Termux; если нужны device-команды — совместимый Termux:API и пакет `termux-api`. Не смешивать произвольно источники/подписи этих двух приложений.
2. Выдать Moru разрешение запускать команды Termux и включить `allow-external-apps`. Moru должен понятно объяснить, что это широкое право, а мини-приложению выдать только отдельную выбранную возможность.
3. Для конкретных API выдать Android-разрешения Termux:API; для обмена файлами выбрать папку/документ либо настроить общий каталог.
4. Если нужны длительные задачи, проверить ограничения батареи/фона Termux и Moru. Не просить отключать оптимизацию всем приложениям заранее.

В основном upstream Termux сейчас `targetSdkVersion=28`; это не утверждение о каждой Play/форк-сборке. Для запрета cross-app `startForegroundService` Android 12 важны target SDK **обоих** приложений [A8]. Даже если конкретная проверка не применяется, остаются Doze, ограничения фоновых Activity и убийство процессов. Поэтому «RUN_COMMAND всегда работает из фона» — неверное обещание.

### Когда какое окружение лучше

| Задача | Выбор | Почему |
| --- | --- | --- |
| Панель батареи, яркость, режимы телефона | **Нативный Moru** | Меньше переходов/процессов, единые права и состояние. |
| Пользователь уже настроил Termux, у него скрипты и Termux:API | **Необязательный адаптер Termux** | Можно использовать готовую среду без переносов; нужны настройка и контроль широкого права запуска. |
| Python/Node, обычные Linux-пакеты, MCP, обработка файлов Moru | **Встроенный Linux PRoot** | Уже связан с workspace и lifecycle Moru; другой APK не требуется. Не приобретает Android-root. |
| Большая работа с частыми системными вызовами на уже rooted-телефоне | **Root chroot Moru, только для доверенной задачи** | Нет PRoot-перехвата системных вызовов; скорость зависит от задачи. Root не должен автоматически попадать любому мини-приложению. |
| Долгая фоновая обработка или локальный сервер | **Любой вариант только с явным lifecycle и ограничениями** | И Moru, и Termux подчиняются Android/OEM. Отдельный APK не гарантирует вечную работу. |

**Можно полностью обойтись без Termux** для первого этапа, ИИ-действий и большинства Linux-задач Moru. Termux — совместимость для уже существующей пользовательской среды, а не обязательная часть нового движка.

## 6. ИИ ↔ мини-приложение: предлагаемый контракт

### Общий путь

**Манифест действий → реестр инструментов ИИ → общий исполнитель → проверки прав и подтверждение → выполнение → фактическое состояние → обновление UI.** Кнопка входит в тот же исполнитель перед проверками. Нет второго скрытого пути «для ИИ» или «для кнопок».

1. При публикации Moru проверяет описание приложения: версия формата, движок экрана, список действий. Каждое действие имеет имя, понятное описание, исходную JSON-схему аргументов, исполнитель, необходимые возможности, требование root и подтверждения. Манифест просит права, но не выдаёт их и не может понизить встроенную политику Moru.
2. Включённые для текущего ассистента приложения дают инструменты вида `ma_battery_control_set_brightness`. Реестр хранит соответствие имени настоящему app/action ID и версии. Имена ограничиваются по длине/символам, проверяются на коллизии с локальными/MCP-инструментами; приложение не подменяет `root_shell` или системное имя. При большом количестве — выбор приложений/действий, чтобы не раздувать каждый запрос модели.
3. Их исходные schemas проходят **уже существующий** normalizer PR #106 при сборке запросов OpenAI, Claude и Gemini; ACP получает действия через существующий MCP-адаптер с явной проверкой допустимости. Не создавать второй нормализатор и не менять сохранённую исходную схему.
4. Исполнитель проверяет аргументы по исходному контракту и своим типизированным ограничениям. Нельзя полагаться на модель: Gemini может получить лишь описание некоторых ограничений, а strict OpenAI — nullable для необязательных полей. Значение `null` должно иметь заранее заданный смысл, а не превращаться в нулевую яркость/смену режима.
5. Проверяются приложение и его версия, live-права ассистента, права приложения, Android-разрешения и доступный backend. Перед подтверждением строится конкретное действие; после ожидания проверяются владелец вызова, аргументы и актуальные права снова. Удаление/обновление приложения, отзыв права или Stop не должны исполнять старый ожидающий запрос.
6. После выполнения Moru читает результат Android. Ответ сообщает `applied`, `opened_settings`, `permission_required`, `unsupported`, `denied`, `failed` или `unknown_after_timeout`, а также обновлённые значения. Открытый экран настроек — не подтверждение включения режима. Не заставлять ИИ говорить «включено», когда выполнен лишь переход в настройки.

Это **предложение**, не манифест, который текущий Moru уже исполняет. Сокращённый пример первых действий:

| **Скрытый WebView** | Браузер, загрузка HTML/JS, мост. Уже есть таймауты. | Совместимость с существующими JS-функциями, которым нужен браузер. | Не выбрать для простого device-действия. Нужны отдельная экспортированная функция, без побочных эффектов загрузки UI, и контролируемый срок жизни. |

Серверная функция не заменяет разрешения на Android. |

`moru.ai.ask` сегодня делает отдельный текстовый запрос модели, а не автоматически экспортирует действия мини-приложения в чат. В первом этапе управление кнопками выполняется локально без обращения к ИИ; чат вызывает зарегистрированные инструменты. Распознавание естественного языка у модели может занимать секунды и зависеть от сети, даже если локальный исполнитель быстрый. Эти задержки измеряются отдельно.

### Как синхронизировать состояние

Сейчас внешняя запись MiniAppStore отправляет событие изменения ключа, а MiniAppPage вызывает `moru:storage`; запись из самого приложения с `fromApp: true` такого события не отправляет. Очередь защищает последовательность записей внутри одного store, но не создаёт транзакционный device-state. В [MiniAppWebServer](../../lib/core/services/mini_apps/mini_app_web_server.dart) также нет готового push-канала этих изменений в удалённый браузер.

Предложение:

- **Android — источник истины для настроек телефона.** Moru держит свежий снимок в памяти: значения, время чтения, доступность полей, `revision`. Не хранить «якобы включённый» режим как обычный writable ключ приложения.
- Кнопка и ИИ выполняют одну команду; команда задаёт значение (`enabled: true`), а не «переключи». Это безопаснее при повторном запросе. Исполнитель после действия читает фактическое состояние и публикует изменение.
- Открытые Flutter-экраны получают узкие подписки; WebView — компактное событие `moru:device`/`moru:state`. UI сразу обновляется и при внешнем изменении через Android-настройки. Закрытое приложение не нужно держать живым: при следующем открытии оно получает новый снимок.
- Сохранять отдельно предпочтения/пресеты и редкую историю. Высокочастотные показания не должны каждую секунду переписывать `data.json`. Если нужна запись состояния приложения — ревизии и атомарный update с проверкой старой версии, а не несогласованные read → write.
- Общие настройки, например яркость, сериализовать между приложениями и ИИ; конфликт с действием пользователя обнаруживать повторным чтением. При повторном подключении отдавать снимок и revision, а не надеяться на сохранность всех событий.
- Результаты ограничивать по размеру; не отправлять в контекст ИИ весь журнал и 5 MiB данных. Для истории — страница/сводка. Учитывать уже отмеченное ограничение [аудита D7](../audits/model-tools.md).

## 7. Безопасный `moru.device.*`

### Три независимых решения о доступе

**Право Android → право конкретного мини-приложения → согласие на конкретное изменение.** Все три проверяются в Moru, а не в JS или тексте для модели.

При первом использовании возможность объясняется простым текстом: «Эта панель хочет менять общую яркость». Пользователь видит источник вызова — кнопка, ИИ, расписание — и выдаёт/отклоняет доступ. Системный экран Android открывается только если нужно его разрешение. Запросы из фона без доступного интерфейса возвращают `permission_required`, а не висят и не разрешают сами себе.

В карточке приложения должны быть видны и отключаемы каждое право, root-доступ и действия для ИИ/фона. Обновление/откат приложения не расширяют права молча; новые права запрашиваются отдельно. Решения связываются с проверенной версией/действием. Полный доступ снимает повторное подтверждение Moru, но **не** отменяет типы/лимиты/белый список, не выдаёт root и не превращается в разрешение любому новому приложению. Право ИИ использовать приложение также отдельно от установки приложения.

Для кнопки обычное явное нажатие может служить согласием на конкретное безопасное изменение после выдачи возможности. Для ИИ-изменений — карточка ToolApprovalService, если полный доступ выключен. Для root-действий — отдельное подтверждение и для кнопки, и для ИИ, либо полный доступ при уже выданном приложению root-праве. Сначала подготовить понятное изменение, затем спросить; никогда не менять аргументы после согласия.

### Root — фиксированные операции, без произвольной строки

В первом этапе mini-app API не имеет `execRoot(command)`, `shell(command)` или записи произвольного ключа Settings. Есть, например, только `device.powerSave.set(enabled)`; код Moru сам выбирает проверенную команду и аргументы. Для чтения — конкретные `settings get`/diagnostic подкоманды, а не весь `dumpsys`. Для записи — точный ключ, область, тип и границы. Никаких substitutions, pipes, перенаправлений, путей из модели или «попробовать команду, которую придумал ИИ».

Нужны: безопасная сборка argv/строго фиксированная shell-шаблонизация, timeout, ограничение вывода, отмена процесса, проверка доступности команды, чтение результата и повторная проверка прав. `RootShellTool.isReadOnly` для этого не использовать. Полный доступ отключает диалог, **сохраняет** список операций device API. Экспертный `root_shell` остаётся отдельной явно включённой возможностью чата, не выдаваемой мини-приложению через мост.

Ограниченное приложение не запускает `server.command` с наследованным root chroot. Нужен отдельный непривилегированный выбор runtime или отказ до запуска. Если пользователь отдельно разрешает произвольный доверенный root-сервер/Termux shell, это другой уровень с честным объяснением: обещать белый список device API для такого кода уже нельзя. Даже непривилегированный PRoot под UID Moru требует оценки доступа к файлам/секретам Moru; read-only mount — недостаточная защита.

Мост должен брать app ID/версию/владельца из доверенного контекста, а не из аргументов страницы. Для WebView не допускать привилегированные вызовы от чужого iframe/origin; сетевой whitelist `moru.fetch` не контролирует автоматически обычный браузерный `fetch` и загрузку ресурсов. Для Linux/Termux использовать broker token с ограниченными правами, сроком жизни и проверками, не выдавать ему `su` или общий tool handler.

**Wi-Fi-веб-хост:** новые device/root-возможности по умолчанию выключены для этого входа. HTTP Basic без TLS не шифрует пароль/действия; пароль может быть вообще отключён. Если понадобится удалённый пульт — отдельные аутентификация, защита CSRF/origin, шифрование и пользовательское сопряжение. До этого удалённый HTML не должен наследовать доступ «потому что это то же приложение».

### Набор первого этапа

| Предлагаемый метод | Польза | Доступ/защита |
| --- | --- | --- |
| `moru.device.capabilities()` | Узнать доступные чтения/действия и причину недоступности. | Без опасных изменений; root не пробовать многократно ради статуса. |
| `moru.device.battery.getStatus()` | Заряд, зарядка, источник питания, температура, доступность доп. полей. | Возможность чтения для приложения; неизвестное значение — `null` с причиной. |
| `moru.device.power.getStatus()` | Реальное состояние энергосбережения и экрана. | Чтение; не смешивать с правом менять режим. |
| `moru.device.brightness.get()` | Общая яркость/авторежим и режим окна. | Явно указывать область действия и единицы. |
| `moru.device.brightness.set({percent})` | Общая яркость без root при WRITE_SETTINGS; root-адаптер при необходимости и отдельном праве. | Первая версия: безопасный минимум, commit после отпускания ползунка, сохранение/восстановление прежнего режима. Изменение авторежима заранее показывать пользователю. |
| `moru.device.powerSave.set({enabled})` | Прямое включение/выключение с root. | Фиксированный обработчик, отдельное root-право, подтверждение/полный доступ, проверка `isPowerSaveMode`. Без root — `unsupported`, а не скрытое нажатие настроек. |
| `moru.device.settings.open({page})` | Открыть батарею, энергосбережение, яркость, выдачу WRITE_SETTINGS. | `page` из небольшого enum. Не принимать произвольный Intent/команду, сообщать `opened_settings`. |
| `moru.device.subscribe({events})` и отмена подписки | Обновление батареи/режима/яркости/экрана, пока панель открыта. | Ограниченные события, shared native subscriptions, coalescing; никакого вечного WebView. |
| `moru.device.restore({changeId})` | Вернуть настройки, которые изменила панель. | Только собственный записанный набор изменений; не затирать более позднюю ручную настройку. Тот же уровень прав/подтверждений. |

В первый этап **не включать** отключение пакетов, force-stop, appops, общую частоту, CPU/GPU, зарядные пороги и автоизменения по температуре. Это отдельные проверяемые возможности, а не скрытые части кнопки «Оптимизировать».

## 8. Производительность и батарея

Главная оптимизация — **не держать исполняемый код там, где достаточно прочитать состояние или выполнить одно действие**. Экран панели может быть закрыт, но инструмент ИИ остаётся доступным через нативный исполнитель.

### Модель работы

- Один нативный слой получает `ACTION_BATTERY_CHANGED`, изменения энергосбережения, экран и network callbacks. Включает только необходимые подписки, когда есть подписчики; раздаёт снимки заинтересованным приложениям. Для сети используем уже объявленное `ACCESS_NETWORK_STATE`, без опроса сокета каждые секунды.
- Соединить быстрые события и передавать только изменённые поля. Как начальная политика для проверки: UI батареи обновлять не чаще раза в секунду; температуру/расчёт расхода реже, например раз в 10–30 секунд **только на открытом экране**. Это предложенные лимиты, а не факт о скорости датчиков.
- Яркость показывать локально при движении ползунка, выполнять запись при отпускании; при необходимости промежуточные записи ограничить. Не запускать root-процесс на каждый пиксель движения.
- Дополнительную статистику расхода запрашивать по кнопке/редко; `dumpsys batterystats` не использовать как секундный датчик. Историю ограничить и записывать пакетами.
- Linux/Termux/VM получать на время действия, ограничивать параллелизм и результат, прекращать после завершения/таймаута. Постоянный сервер включать только явно. Не устанавливать runtime и зависимости при каждом открытии.
- После закрытия панели нет её WebView, серверов, VM и timers; данные/пресеты сохраняются. Системное изменение яркости/режима может оставаться, если это выбранное пользователем поведение, но не должно требовать живого процесса панели.
- Для батарейной панели `keepAwake=false`, не требовать постоянного foreground service. [ProcessKeepAlive](../../lib/core/services/keep_alive.dart) использует уже существующий [GenerationForegroundService](../../android/app/src/main/kotlin/com/psyche/kelivo/background/GenerationForegroundService.kt), который удерживает `PARTIAL_WAKE_LOCK` во время работы. Держать Linux-сервер «на всякий случай» в такой схеме особенно нежелательно.

**Ограничение событий:** обычная динамическая подписка работает, пока жив процесс. `ACTION_BATTERY_CHANGED` нельзя превратить в гарантированный постоянный монитор через обычный manifest receiver. После force-stop Android не обязан разбудить Moru. Для порога «при 20% включить режим даже с закрытым Moru» нужна отдельная модель разрешённой фоновой работы, допустимые системные события/планировщик и честная гарантия. Периодический WorkManager имеет минимум 15 минут и может запаздывать; AlarmManager/Doze/OEM также не гарантируют секунды [A11], [A12]. В первом этапе постоянный монитор не обещать.

### Как измерить в будущей реализации

1. Зафиксировать одинаковый телефон, Android/прошивку, WebView, release/profile сборку, яркость, сеть, температуру и зарядку. Отдельно тестировать root/non-root, холодный Moru и уже открытый Moru. Эмулятор/host-тесты не доказывают расход батареи телефона.
2. Измерить время до видимого пригодного экрана и до первого свежего состояния; нажатие/ИИ-tool dispatch → начало исполнения → фактическое изменение → UI. Диалоги, задержку модели/сети и старт root-менеджера учитывать отдельно. Сравнивать медиану и p95, а не единственный удачный запуск.
3. Проверить кадры Flutter и WebView при ползунке/графике: долю пропущенных кадров, p95/p99 frame time, build/raster, main-thread stalls. Бюджет кадра — около 16,7 мс при 60 Hz и 8,3 мс при 120 Hz, а не универсальные 16 мс. [FlutterLogger](../../lib/core/services/logging/flutter_logger.dart) ловит грубые задержки >100 мс, но не заменяет полную трассу.
4. Снять память всего приложения **вместе с renderer/дочерними процессами**, PSS/RSS, native heap и пиковые значения. Посчитать CPU-время, wake locks, пробуждения, переходы через мост, частоту записи диска и число живых процессов после закрытия [P1], [P2].
5. Сравнить длительные одинаковые сценарии: без панели, открытая панель без действий, повторные действия, закрытая панель/погашенный экран, работа фонового правила. Power rails/Perfetto доступны не на каждом телефоне; проценты батареи за пару минут слишком грубы. Повторы с контролем внешних условий, без обещания точности ниже возможностей датчика [P3].
6. Проверить размер подписанного arm64 release APK и размер скачанных rootfs/пакетов отдельно. Debug APK и крошечный пример QuickJS на Linux не дают нужное число.

Android обычно учитывает приложения и их процессы по UID. Мини-приложения и PRoot-программы Moru не получают отдельные UID, поэтому нельзя обещать системный процент батареи для каждого из них. Для собственного UID доступны ресурсные HealthStats [A18]; раздельные counters/call timings внутри Moru могут помочь диагностике, но не дают точного расхода энергии каждой панели.

Предлагаемые критерии приёмки: после закрытия нет ресурсов панели; нет периодического AI/root опроса; отключение прав действительно прекращает доступ; ползунок не запускает цепочку процессов; кнопка и ИИ возвращают одинаковое проверенное состояние. Численные цели запуска/памяти/батареи выбрать после первого профиля на устройстве пользователя. Исследование не утверждает, что ускорение уже получено.

## 9. Варианты, которые могут быть полезнее исходного предложения

**Нативные действия без собственного скрипта — лучший первый шаг.** ИИ не обязан писать программу вычисления для каждой кнопки: он связывает готовое действие с готовым компонентом. Можно быстро собирать батарею, сеть, звук и другие панели по мере добавления безопасных возможностей. Произвольная логика появляется позже, когда есть подтверждённая потребность.

**Пресеты и простые локальные правила:** пользователь просит «режим для дороги», ИИ предлагает конкретный проверяемый набор изменений. При применении Moru показывает последствия, выполняет ограниченные действия, сохраняет прошлые значения и позволяет восстановить их. Сам пресет не запускает ИИ в фоне. Нельзя обещать атомарность нескольких Android-настроек: частичный отказ/откат нужно явно показывать. Фоновые условия — отдельный этап после решения ограничений Android.

**Shizuku как промежуточный уровень** [S1]: многие shell-операции доступны без root через сервис, запущенный ADB. На Android 11+ обычно можно запускать его через wireless debugging на устройстве; на Android 10 обычно нужен внешний ADB либо root. Пользователь запускает/разрешает сервис, после перезагрузки может потребоваться повторный запуск; OEM/сеть могут мешать. Shizuku не получает всё, что доступно root, не снимает SELinux и не даёт универсальный cpufreq. Для энергосбережения/части appops полезнее, чем требовать root всем; интеграции в текущем Moru нет. Это отдельный backend тех же ограниченных действий, а не произвольная shell-консоль для мини-приложения.

**Готовая автоматизация пользователя — Tasker и аналоги:** если у пользователя уже есть нужный сценарий, точечный проверяемый вызов может быть дешевле разработки общего движка. Нужны настройка, разрешения, отдельная оценка поддерживаемого API/версии; эти приложения не обходят Android самостоятельно. Обязательную платную зависимость для первой панели не вводить.

**Quick Settings tile / виджет / ярлык пресета:** позже дадут управление без открытия полного Moru; должны вызывать тот же исполнитель и показывать фактическое состояние. Включение root-действия без подтверждения требует уже явно выбранной политики. Это может дать больше практической скорости, чем смена JS-движка.

**WASM:** полезен для конкретного тяжёлого вычисления или библиотеки в веб-приложении; не заменяет UI/device API и не даёт новых Android-прав. Для батарейного переключателя усложняет работу без пользы. Отдельные генерируемые APK/нативные плагины также требуют сборки, подписи и другой модели безопасности; их не стоит выбирать вместо маленькой панели Moru.

Таким образом, «чтобы всё летало» лучше достигается коротким локальным путём, предсказуемыми компонентами и отсутствием фоновой работы, чем обязательным QuickJS, Python или новым игровым движком для любого приложения.

### Что получит пользователь после первого этапа

Открывает «Контроль батареи» и видит свежий заряд, температуру батареи, зарядку и состояние энергосбережения. Может поменять яркость или восстановить прежнюю. Без root кнопка энергосбережения открывает системный экран, а после возврата панель перечитывает состояние. С root — выполняет прямое действие после согласия либо в полном доступе.

В чате «покажи состояние батареи», «сделай яркость 40%» и «включи энергосбережение» идут через действия **этой же панели**. Для последней команды на non-root телефоне ИИ объясняет необходимость настройки и может открыть её при доступном UI; не пишет ложное «готово». При отсутствии WRITE_SETTINGS/foreground Activity/root-grant сообщается конкретная причина и способ её устранить. Закрытая панель для выполнения нативного действия не открывается и не остаётся процессом в фоне.

## 11. Риски, ограничения и вопросы

| Риск / то, что нельзя обещать | Защита и честное поведение |
| --- | --- |
| Точные проценты расхода по всем приложениям, универсальный износ/остаток времени | Отдельно активность, измеренные датчики и оценка. Показывать источник/время и «нет данных». Не выдавать screen time за энергопотребление. |
| Root/ADB-команда завершилась, но OEM не применил режим | Readback через Android; результат `failed/unsupported/unknown`, без автоматического перебора опасных команд. |
| Полностью гарантированный мгновенный фон, работа после force-stop/перезагрузки | Ограничения Android/OEM показывать заранее; отдельная настройка и проверки. Не держать скрытый WebView/сервер ради обещания, которое Android не гарантирует. |
| Очень низкая яркость, потерянный авторежим, перебой связи/уведомлений | Безопасные диапазоны, сохранение прежних настроек, понятная область действия и восстановление. Первым этапом не ограничивать чужие приложения и радио. |
| Root Linux/Termux/старый инструмент обходят новый белый список | Запрет автоматического наследования привилегированного executor, независимые capabilities, проверка всех входов. Не заявлять безопасность для отдельно разрешённого произвольного root-кода. |
| Приложение обновилось после согласия, два источника спорят о настройке | Привязка вызова к версии/аргументам/владельцу; проверки после каждого ожидания, сериализация глобальных изменений, ревизии и повторное чтение. |
| Stop или timeout наступил после системного изменения | Отмена ожидания не всегда отменяет уже выполненный side effect. Перечитать состояние; сообщить частичный результат и предложить собственное восстановление. Не обещать физическую отмену без доказательства. |
| Отмена/откат разрушает более позднюю ручную настройку | Хранить before/after/change ID; восстанавливать только если текущая настройка соответствует своему последнему изменению, либо спрашивать отдельно. Откат исходников mini-app не откатывает телефон. |
| Скрипт зациклился, сервер потребляет батарею, данные растут | Лимиты времени/памяти/частоты/вывода, bounded история, явные владельцы и остановка; не запускать общий VM в UI-потоке. |
| Чужой iframe, LAN-браузер, приложение телефона или содержимое экрана обращаются к API | Origin/app-bound контекст, tokens, отключённые remote device-права, проверка запросов и независимые capabilities. Текст UI/описание стороннего приложения — данные, а не инструкция ИИ выдать разрешение. |
| `/sys`/cpufreq, отключение thermal-защиты, зарядные параметры вредят телефону | Исключить из обычного API; не угадывать vendor-пути. Даже root и полный доступ не делают такую автоматику безопасной. |
| Ложная «оптимизация»: симуляция батареи, сброс статистики, убийство всех приложений | `dumpsys battery set/unplug` — тестовая подмена показаний, не управление зарядом. Сброс batterystats не калибрует физическую батарею. Постоянные force-stop могут увеличить расход из-за перезапусков [A16]. Такие операции не включать в панель. |

До реализации нужно уточнить у пользователя:

1. Какие телефоны, версии Android и прошивки должны поддерживаться в первую очередь? Есть ли Magisk/KernelSU, и предоставлен ли root именно Moru?
2. Достаточно ли без root открывать системное энергосбережение, или пользователь готов отдельно настраивать Shizuku/ADB ради прямого переключения?
3. Нужен только пульт по запросу или гарантированное правило при закрытом Moru/погашенном экране? Второе требует отдельного решения с меньшими гарантиями на некоторых прошивках.
4. «Какие приложения тратят заряд» — достаточно системного экрана/оценочной статистики или нужен собственный график? Время использования и энергия — разные показатели.
5. Установлен ли Termux, какая сборка, есть ли Termux:API и существующие скрипты, ради которых нужна интеграция?
6. Что восстанавливать при закрытии панели: яркость окна автоматически, общие настройки по кнопке или временный режим на заданный срок? Автовосстановление общих настроек не следует навязывать.
7. Должны ли устройства управляться из Wi-Fi-веб-хоста? Для первого этапа рекомендуется оставить доступ локальным в Moru/чате.
8. Какие действия ИИ можно выполнять без повторного подтверждения, и будет ли пользователь использовать полный доступ? Возможности каждого приложения должны оставаться видимыми и отключаемыми.
